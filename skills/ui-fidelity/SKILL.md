# UI 还原工作流（design → code）

把一屏设计稿完整还原成代码。**一次只做一屏**——多屏就重复本流程，不要一把梭。

权威依据：若目标项目 `CLAUDE.md` 写了「UI 还原协议」之类的规约，则以其为准，本 skill 是它的可执行版；项目没有这类规约时，本 skill 自成准则。

## 适用与输入

- **设计源**：一个 PNG 路径（如 `specs/ui/<模块>/<屏>.png`、`design/<屏>.png`），或一块 `.pen` 画板（仓内某个 `*.pen` 文件的某个节点）。
- **目标**：要落地到哪个仓 / 路由 / 组件。**不确定落点（仓 / 路由 / 用哪个前端框架与组件库）时先问用户，别猜。**

## 步骤（顺序执行，不可跳步）

### 0. 定源 —— 拿到真正的设计像素

- **`.pen` 源**：先 `mcp__pencil__get_editor_state(include_schema: true)` 确认 Pencil 桌面应用已连上。
  - **连不上（报 `transport not connected`）→ 立刻停下**，告诉用户「请在 Pencil 桌面应用中打开 `<文件名>.pen`」，等用户确认后再继续。**绝不凭文件名 / PRD 文字脑补布局**。
  - **以「活动文档」为准，别信 `filePath`**：实测 `filePath` 参数常不被采纳，读到的是当前活动文档。`get_editor_state` 的 `Currently active editor` 必须正是目标 `.pen`；若不是，让用户在 Pencil 里切到该文件（点开它的 tab）再继续。读到的画板名/内容要与目标功能对得上（如出现「Welcome to Pencil / Step Frame / rover」等欢迎模板内容，说明拿错了文档）。
- **PNG 源**：直接用 `Read` 打开该图，亲眼看到再继续。
- **逐屏读图**：本屏涉及的每张图 / 每块画板都要真的打开看过。
- **低清整屏图必须先放大再判读**：当 PNG 是平台整屏截图、目标面板只占其中一小块（如某 ~600px 宽图里工具栏仅 ~240px）时，**禁止**直接从整屏图断言某控件"存在 / 不存在"。必须先把目标面板区域裁剪放大再看：`sips -c <h> <w> -i <png> ... ` 或 `magick <png> -crop WxH+X+Y +repage out.png` 落到临时文件再 `Read`，或分区多次 `Read`。
- **结构/交互看不清 → 停下来问**（与 `.pen` 连不上就停同级纪律）：放大后仍无法确认某 **affordance/结构**（行首展开箭头 ▼、小图标、角标、嵌套子行、复选框）到底有没有 → **立刻停下，把"这里看不清是不是 X"明确问用户**，不得脑补成"没有"。这是把旧规则「颜色/字号量不准→向用户索取」扩展到「结构/交互量不准→停」。

### 0.5 枚举图集 + 建状态/交互矩阵（不可跳——本步专治"只还原默认态"）

一屏往往不止一张图、不止一个状态。先把"本屏到底有哪些状态要还原"钉死，再动手，否则收拢/展开、选中、空态这类**结构性交互**会整类漏掉。

- **列全图集**：`ls specs/ui*/<模块>/`（或设计目录、或 `.pen` 的全部相关画板）。**文件名就是状态规格**——`（收起）`/`（修改后）`/`（审查中）`/`-选中项目`/`-本地上传`/`-单个历史报告` 等后缀，每一个变体都是一个**必须实现且必须截图验证**的状态。**变体图数量 = 本屏状态数下限。**
- **逐元素枚举状态**：对每个交互控件，列出它的全部状态及"触发后揭示什么"——default / hover / 选中 / 禁用 / 空 / 加载 / **展开-收拢** / 主从 / 树形 / 分页 / tab 切换。行首有 ▼ 就意味着"能展开"——必须查清展开后是什么（子行？嵌套版本？明细？）。
- **前置结构 ↔ 数据对账**：某结构性 affordance（如"项目行展开成版本列表"）若在 PRD / 数据模型 / 后端端点里查无对应 → **在实现前**就归入「建议确认」抛给用户，别等 Step 3 写到一半才发现冲突。
- **产出状态矩阵**（贯穿到 Step 5 收口）：

  | 元素 | 状态 | 对应设计图 | 已实现 | 已截图验证 |
  |---|---|---|---|---|
  | 项目行 | 收拢 | 2项目选择-在线选择.png | ☐ | ☐ |
  | 项目行 | 展开(版本列表) | （需向用户确认/补图） | ☐ | ☐ |
  | 项目行 | 选中 | 2项目选择-选中项目.png | ☐ | ☐ |

  每一行后续都要走到"已实现 + 已截图验证"才算这屏完成。

### 1. 抽规格 —— 精确 token，不靠肉眼

- **`.pen`**：
  - `mcp__pencil__get_variables` 抽全局设计 token（颜色 / 圆角 / 字体变量）——这是精确调色板的来源，**优先用它而非肉眼取色**。
  - `mcp__pencil__export_nodes` 把目标画板导出为高清参考 PNG（建议落到项目的设计基线目录，如 `specs/ui/<模块>/`，纳入权威基线），再 `Read` 出来全分辨率看。**注意：export_nodes 一次只传一个 nodeId**，多个会报 `wrong .pen file`；逐个导出。
  - `mcp__pencil__snapshot_layout` 取精确布局尺寸；`mcp__pencil__batch_get`（必要时 `resolveVariables: true`）取颜色 / 字号 / 间距 / 组件层级的数值。
- **PNG**：逐元素枚举可见信息（区块、组件、相对位置、可量出的间距、文案）。颜色 / 字号若图上量不准，向用户索取或参考设计系统 token。
- 产出**精确 token 清单**：颜色（十六进制）、字号、行高、间距/留白、圆角、组件尺寸（宽高）、栅格列宽。不要写 "蓝色按钮"，要写 "`#1890ff`，高 32px，圆角 4px"。
- **token 必须落成命名变量，不准散落数值**（研究结论：「引用 token 而非肉眼近似数值」是保真的根）。抽出的色值/间距/字号映射到目标仓的 theme 变量（CSS var / TS theme / 目标仓 UI 框架的设计变量，如 Element Plus / view-ui-plus / Ant Design / Tailwind 等，以实际为准），代码里引用变量名而非把 `#1890ff` 直接写死在各处。已有同名 token 就复用，缺的才新增。
- **产出 `设计稿元素 → 前端组件` 映射表**（这是对 Figma `Code Connect` 的人肉替代——`.pen` 加密、没有自动绑定机制，不显式列映射 agent 就会重写而非复用既有组件）：

  | 设计稿元素（.pen 节点 / 截图区块） | 目标仓真实组件 | 备注（变体/props） |
  |---|---|---|
  | 顶部主按钮 | 目标仓的 `<Button type="primary">`（示例） | size=default |
  | 项目列表行 | 复用既有 `ProjectRow.vue`（示例） | 勿新建 |
  | 指标树 | 目标仓的 `<Tree>`（示例） | 行首 ▼ = expandable |

  （上表仅为示例，组件名/框架以目标仓实际为准。）映射不确定（某设计元素在目标仓查无对应组件）→ 归入「建议确认」抛给用户，别擅自造新组件。

### 2. 建逐屏验收清单

按这些维度逐项列出本屏的期望值，作为后续比对的对照表：

| 维度 | 内容 |
|---|---|
| 布局区块 | 顶栏 / 侧栏 / 主区 / 面板的划分与占比 |
| 组件 | 每个控件类型、数量、排列 |
| 间距 | 区块/控件间距、内边距 |
| 颜色 | 背景 / 文字 / 主色 / 边框 |
| 字号 | 标题 / 正文 / 辅助文字 |
| 交互/结构 | 本屏的结构性交互：行展开-收拢 / 主从 / 树形 / 分页 / tab 切换 —— 对照 Step 0.5 状态矩阵逐一列 |
| 状态 | 每个控件的**全部**状态（不止这五个）：hover / 选中 / 禁用 / 空态 / 加载 / **展开-收拢** …… 以状态矩阵为准，别用固定五项当上限 |
| 状态覆盖 | 状态矩阵里每个状态是否都已实现且已截图验证（未验证 = 未还原） |
| 文案 | 按钮、标签、占位符的确切文字 |

### 3. 实现到目标仓

- **严格按 Step 1 的组件映射表落地**：映射表里写了「复用 X 组件」的就复用，**不准重写一个视觉近似的新组件**；颜色/间距/字号引用 Step 1 建的命名 theme 变量，不准散落硬编码数值。
- 复用目标仓既有组件库与设计 token（以目标仓实际用的 UI 框架为准），别重造。
- **完全还原非补丁**：本屏要逐区块重建到位，**清除旧界面残留控件**，不是只改点出的几处。
- 设计稿与既有功能约束冲突时（如设计要多选但数据模型是单选）→ **显式标注，让用户拍板**，不默默折中。

### 4. 验证 —— 两条独立验证线（视觉保真 ⊥ 交互行为）

> 研究结论：**视觉像素对上 ≠ 功能正确**——agent 常能复现视觉结构却把交互做错（实测 CLIP 视觉相似 0.85 但行为分仅 0.28，二者部分解耦）。所以视觉和行为**必须分两条线各自验**，任一条没过都不算还原完成。

先用 **dev-browser** 启动/确认目标仓 dev server（端口以目标项目为准；统一 dev-browser，禁用 playwright / claude-in-chrome），导航到本屏。

**线 A — 视觉保真线**

- **逐态截图，不止默认态**：按 Step 0.5 状态矩阵，**主动把 UI 驱动进每一个状态**再截——点开行展开、点选中、清空筛选触发空态、切 tab…… 每个状态一张图，文件名带状态（如 `proj-collapsed.png` / `proj-expanded.png` / `proj-selected.png`）。
- **量化预筛：CV 对齐 diff**（消除裸 pixel-diff 的错位假阳性）。对每个「实现截图 ↔ 设计参考图」配对跑：

  ```bash
  python3 ~/.claude/skills/ui-fidelity/scripts/visual_diff.py \
    --design <设计参考.png> --impl <dev-browser截图.png> --out /tmp/vdiff-<状态>
  # 首次需: pip install opencv-python numpy （一次性本地依赖）
  ```

  它先用 ORB 把实现图对齐到设计图坐标系（杀掉 1-2px 平移假阳性），输出 `diff.json`（每个差异块的 **bbox + 面积占比 + mean_delta**）+ 红框标注图。读 `diff.json`：`mean_delta` 大的块是真改动，`mean_delta` ~10 的多是抗锯齿残留可忽略；`alignment_method=resize-fallback` 说明对齐失败、结果仅供参考。**这一步只回答「该看哪几个坐标」，不做语义判定。**
- **语义裁判：`ui-fidelity-reviewer` 子代理**（若目标项目无此 agent，则用通用 review 子代理 / `Explore` 做独立第二双眼比对）。把 **整组实现截图 + 整组设计参考图 + Step 0.5 状态矩阵 + 各状态的 `diff.json`（含 bbox）** 一起传给它（不是只传默认态两张图），拿回逐项差异清单 + 状态覆盖审计。bbox 让 reviewer 聚焦坐标、把差异归到 content/style/layout/size 哪一类。
  - （子代理只读、只出清单；"写"由你负责，职责分离。CV diff 是量化预筛，reviewer 是语义裁判，二者配合不互替。）

**线 B — 交互行为线**

- 对状态矩阵里每个**结构性交互**，在 dev-browser 里**实际驱动并断言行为真的发生**，而不只是「截图长得像」：
  - 点行首 ▼ → 确认**真的展开**出子行/版本列表，且数据正确（不是只换了个箭头图标）。
  - 点选中 → 确认选中态 + 下游联动（如选中项目后版本区真的刷新）。
  - 清空筛选 → 确认**真的进空态**而非报错/白屏。
  - 切 tab / 分页 / 提交表单 → 确认内容真的切换/翻页/提交成功，控制台无报错。
- 行为对不上但视觉对得上 → 仍记为**未还原**，进 Step 5 修。涉及前后端联动的行为问题走 `/fullstack-test-loop`、跨模块字段契约按调试协议查生产者↔消费者。

### 5. 循环修到一致

- 按差异清单逐条修代码 → 重新 dev-browser 截图 → 重新跑 CV diff + reviewer → 重新比对。
- 循环直到 step2 验收清单全部「一致」**且线 B 交互行为全部断言通过**。
- **迭代要有停止准则，别无限刷**（研究：reviewer 闭环增益集中在前几轮，后续迭代会侵蚀代码质量）。收敛判据：CV diff 无 `mean_delta` 高的真差异块 + reviewer 清单清零 + 行为断言全过。达不成的项归「剩余差异」交用户，而非继续硬磨。
- 收尾时：把**剩余无法消除的差异 / 设计-功能冲突**显式列给用户拍板，**不要**在没截图比对的情况下宣称"已还原 / 已对齐"。
- **哨兵收口铁律**：默认态一致 **≠** 还原完成；视觉对上 **≠** 还原完成。仅当 **(1)** 状态矩阵每一格视觉已验证一致 **(2)** 线 B 每个交互行为断言已通过 **(3)** 或剩余项已显式记为延后且用户签字——三者齐备，才在回复里输出哨兵标记 `ui-fidelity-check-passed`（供有对应 hook 的项目软识别"已走完比对闭环"；无 hook 时它纯作收口标记）。**只截了默认态、整类交互态没验过、或行为没断言只比了截图，就别输出这行。**

## 反模式（这些就是用户踩过的坑）

- ❌ 看文件名 / PRD 文字就开写，没真的打开设计图。
- ❌ `.pen` 连不上却继续脑补，而不是停下来让用户开 Pencil。
- ❌ "蓝色按钮""差不多的间距" 这种肉眼近似，没抽精确 token。
- ❌ 只改我点出的几处、保留旧界面其余部分的最小 delta 补丁。
- ❌ 写完不截图就说"已对齐"。
- ❌ 只截/只比对默认态，整类交互态（展开-收拢、选中、空态）从没驱动出来验过，就宣称"已还原"。
- ❌ 视觉像素对上了就收工，没验交互行为是否**真的工作**（点了展开只换箭头没出子行、清空筛选白屏报错）。
- ❌ 把抽到的色值/间距直接硬编码散落各处，而不落成命名 theme 变量。
- ❌ 不查组件映射、照着设计图重写一个视觉近似的新组件，而不复用目标仓既有组件。
- ❌ 拿裸 pixelmatch 对未对齐的两图 diff，被 1-2px 错位刷满假阳性当成真差异。
- ❌ 从未放大的低清整屏图，凭"看不见"就断言某控件（行首 ▼、小图标）不存在——该放大放大、该停下问就问。
